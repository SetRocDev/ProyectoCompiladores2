1. QUÉ HACE EL PROGRAMA
-------------------------------------------------------------------------------
El programa revisa un archivo de código PHP como lo haría la primera parte de
un compilador, en seis etapas:

  - Análisis léxico (Proyecto 1): corta el código en pedazos (tokens), dice de
    qué tipo es cada uno y revisa que estén bien escritos: nombres de
    variables, etiquetas <?php y ?>, y comentarios // y #.
  - Análisis sintáctico (Proyecto 2): revisa que los tokens estén en el orden
    correcto en las estructuras while, if/else y echo: paréntesis, llaves,
    punto y coma, comillas, bloques vacíos e indentación.
  - Análisis semántico (Proyecto 2): revisa que el código tenga sentido:
    que no se use una variable que nunca recibió un valor y que no se divida
    entre cero.

Al terminar crea un archivo nuevo con el mismo nombre, terminado en
"-errores.log". Ese archivo es una copia exacta del .php con cada línea
numerada, y debajo de cada línea que tiene un problema aparece el error,
indicando qué análisis lo encontró: [Léxico], [Sintáctico] o [Semántico].

El programa funciona solo en consola (CMD). No tiene ventanas ni botones.


2. QUÉ SE NECESITA
-------------------------------------------------------------------------------
  - Una computadora con Windows.
  - Java 8 o una versión más nueva.
    Para comprobarlo: abrir el CMD, escribir
        java -version
    y presionar Enter. Debe aparecer un número de versión.
  - Solo para ver o compilar el código: Apache NetBeans 24 o superior.


3. CÓMO EJECUTARLO (PASO A PASO)
-------------------------------------------------------------------------------
El programa ya viene compilado en la carpeta "dist", junto con el archivo PHP
de ejemplo. Después de descomprimir el .zip en una carpeta con cualquier
nombre:

  Paso 1. Abrir la carpeta del proyecto y entrar a la carpeta "dist".
          Ahí hay dos archivos:
              ProyectoCompiladores2.jar   (el programa)
              CodigoProyecto.php          (el código PHP de la cátedra)

  Paso 2. Abrir el Símbolo del sistema (CMD) en esa carpeta.
          Forma fácil: en el Explorador de archivos, hacer clic en la barra
          de direcciones (donde aparece la ruta de la carpeta), escribir cmd
          y presionar Enter. Se abre el CMD ya ubicado en "dist".

  Paso 3. Escribir este comando y presionar Enter:
              java -jar ProyectoCompiladores2.jar

  Paso 4. En la ventana aparece un resumen como este:
              === Analizador de PHP: lexico, sintactico y semantico ===
              Carpeta: C:\...\ProyectoCompiladores2\dist

              Archivo: CodigoProyecto.php
                Lineas: 53 | Tokens: 148
                Errores: 0 (lexicos: 0, sintacticos: 0, semanticos: 0)
                Log generado: CodigoProyecto-errores.log

  Paso 5. En la carpeta "dist" aparece el archivo nuevo
              CodigoProyecto-errores.log
          Abrirlo con el Bloc de notas para ver el resultado.

  Para revisar otro archivo PHP:
     Copiarlo a la carpeta "dist" y repetir el paso 3. Puede tener cualquier
     nombre, siempre que termine en ".php". Si hay varios archivos .php, el
     programa los revisa todos y crea un .log para cada uno.

  Opciones para ver más detalle (se pueden usar juntas):
      java -jar ProyectoCompiladores2.jar -tokens
          Muestra la lista de tokens (cada palabra o símbolo y su tipo) y la
          tabla de símbolos (cada variable y la línea donde recibe su valor).
      java -jar ProyectoCompiladores2.jar -arbol
          Muestra el árbol sintáctico: cómo entendió el programa la
          estructura del código (qué hay dentro de cada while, if y else).


4. CÓMO LEER EL RESULTADO
-------------------------------------------------------------------------------
El archivo "-errores.log" es una copia exacta del .php, con dos agregados:

  - Cada línea empieza con su número de 4 dígitos y un espacio.
  - Si una línea tiene errores, aparecen en los renglones de abajo, uno por
    renglón, con este formato:    Error NÚMERO. [Tipo] Descripción
    El tipo dice qué análisis encontró el error: [Léxico] (Proyecto 1),
    [Sintáctico] o [Semántico]. Así se distingue, por ejemplo, un while bien
    escrito (sin errores sintácticos) que usa una variable sin valor (error
    semántico).

Todos los errores van debajo de una línea, sin excepción (también los que
dicen que falta <?php o ?>; ver la sección 7).

Ejemplo de una línea con dos errores:

    0036
    0037 while $contador_revision < $cantidad_notas {
    Error 601. [Sintáctico] Falta el paréntesis de apertura '(' después de 'while'; la forma correcta es 'while (condición) {'
    Error 602. [Sintáctico] Falta el paréntesis de cierre ')' de la condición del while
    0038     echo "Revisando nota: " . $notas[$contador_revision] . "\n";

El .log conserva todo el formato del original: espacios, líneas en blanco,
el tipo de salto de línea de cada línea (Windows, Linux o Mac) y la
codificación con que se guardó el .php (UTF-8, o "ANSI" del Bloc de notas),
para que las tildes queden exactamente iguales.

-------------------------------------------------------------------------------
  Forma 1: modificar el archivo de ejemplo.

     2. Cambiar algo. Por ejemplo, en la línea 37 borrar el "(" del while,

            java -jar ProyectoCompiladores2.jar

     La carpeta "pruebas" tiene 127 casos de prueba:
       - pruebas\casos       los archivos .php, cada uno con un error puesto a

                             error que debe aparecer
       - pruebas\herramientas  pruebas extensas opcionales (necesitan

            pruebas\ejecutar-pruebas.bat
     El script ejecuta el programa con todos los casos, compara cada .log con
     el esperado byte por byte y al final muestra:
            Pruebas correctas: 127   Fallidas: 0

  Forma 3: variantes del código de la cátedra (como en el Proyecto 1).
     La carpeta "pruebas\catedra" tiene 616 copias de CodigoProyecto.php,
     cada una con uno, dos o tres cambios: cada error del enunciado en cada
     línea donde puede aparecer y formas válidas que no deben marcarse. Su
     carpeta "esperados" tiene el .log exacto de cada una y su esperado.txt
     dice qué se cambió y qué errores deben aparecer. Para ejecutarlas:
            pruebas\catedra\ejecutar-catedra.bat
     Al final muestra:
            Pruebas correctas: 616   Fallidas: 0

7. CORRECCIONES DEL PROYECTO 1
-------------------------------------------------------------------------------
Estas son las observaciones de la retroalimentación del Proyecto 1, cómo se
corrigió cada una y qué caso de prueba lo demuestra (carpeta pruebas\casos).

  a) Archivo de errores: "si el archivo combina formatos distintos de salto
     de línea, el reporte los unifica".
       Corrección: el programa guarda el salto de línea de CADA línea (CRLF
       de Windows, LF de Linux o CR) y el .log repite exactamente el mismo.
       Además, si el .php termina sin salto de línea, el .log tampoco lo
       agrega (antes agregaba uno al final).
       Pruebas: P24 (mezcla los tres tipos), P25 (solo LF), P26.

  b) Manejo de errores en el .log: "cuando falta la apertura o el cierre,
     coloca el aviso al final sin indicar una línea".
       Corrección: ya no existen errores "sueltos". El 303 (falta <?php) va
       debajo de la línea 0001 y el 305 (falta ?>) debajo de la última línea,
       y el mensaje indica esa línea. Todo el archivo usa la misma opción
       (errores debajo de su línea), como pide el enunciado.
       Pruebas: P10, P27 (sin apertura), P28 (archivo vacío), P29.

  c) Analizador léxico: "la revisión de variables se aplica también a
     nombres después del signo igual; el proyecto pide revisar únicamente la
     variable que recibe el valor".
       Corrección: los errores 201 a 205 solo se revisan en la variable que
       recibe el valor (a la izquierda de "=" o de "+=", ".=", etc.).
       Prueba: P32 ($copia = $1abc . $-d; ya no da error).

  d) Identificadores: "cuando el nombre y el signo igual están en líneas
     distintas puede omitir una palabra reservada o un nombre sin $".
       Corrección: el análisis ya no compara líneas; mira el token anterior
       al "=" saltando saltos de línea y comentarios.
       Pruebas: P30 ($if en una línea y "= 10;" en la siguiente), P31.

  e) Comentarios: "una sola barra al comienzo de una línea se interpreta
     como comentario incorrecto, aunque podría ser parte de una división".
       Corrección: si la línea anterior quedó a mitad de una operación
       (terminó en una variable, un número, ")" o "]"), la "/" es una
       división; si empieza una instrucción nueva, sigue siendo el Error 401.
       Pruebas: P33, P35 (divisiones en dos líneas), P16 (sigue dando 401).

  f) INFORME: "no deja constancia explícita de una comprobación en otra
     computadora".
       Corrección: la sección 14 registra la prueba en otro equipo.

  Problemas que encontramos nosotros y también se corrigieron:
     - "echo PHP_EOL;" daba el Error 402 (texto suelto). Ahora el 402 solo
       aplica a palabras sueltas al inicio de una instrucción (prueba P34).
     - El informe entregado no incluía los prompts principales usados con la
       IA; ahora están en la sección 15.
     - Si el .php se guardaba como "ANSI" (Windows-1252), el .log se escribía
       en UTF-8 y las tildes cambiaban: el .log ya no era una copia exacta.
       Ahora el .log usa la misma codificación del .php y conserva el BOM si
       lo tiene. Pruebas: P109 (UTF-8 con BOM), P110 (ANSI), P111.
     - En la revisión final de código se encontró que algunas expresiones
       válidas de PHP dentro de un echo daban el Error 806 (por ejemplo
       2 ** 3, $a++, $a ?: "x", $obj->nombre). Ahora se aceptan (prueba
       P112). También: "$x %= 0" da el Error 902 (P115), "$1x %= 2" da el
       201 como "$1x += 2" (P116) y un echo con "(" sin cerrar avisa que
       falta el ")" (P113).
     - En la revisión integral final se encontró que una cadena de texto de
       unos 3000 caracteres o más detenía el programa (la expresión regular
       que revisaba las comillas desbordaba la memoria de la pila) y no se
       generaba el .log. Ahora las comillas se revisan carácter por
       carácter (prueba P118), y si un archivo extremo detiene el análisis,
       igual se escribe su .log y se siguen revisando los demás archivos.
       También: los números válidos de PHP como 1e3, 0x1F o 1_000 ya no dan
       errores falsos (P119), y un echo o un else mal escritos ("eco $x;",
       "} els {") dan el Error 504 con la sugerencia, en lugar del 402 de
       texto suelto (P120, P121).
     - Al probar el código de la cátedra con cientos de cambios (sección 13)
       se encontró y se corrigió: un texto antes de "<?php" daba, además del
       301, un 402 por el mismo texto; ahora solo se analiza el código que
       está dentro de las etiquetas (P122). Un while o un if mal escritos
       ("whlie", "iff") se revisan como la estructura que se quiso escribir:
       así aparecen también los demás errores de su línea, por ejemplo el
       paréntesis que falta (504 y 602), y su bloque y su else no dan
       errores en cascada (P123, P125). "fro (...; ...; ...) {" no daba el
       504 por los ";" de la cabecera (P124). Una instrucción sin ";" ya no
       se "traga" un "whlie" o un "eco" de la línea siguiente. Y los
       parámetros de una función anónima, como en usort($notas, function
       ($a, $b) {...}), ya no dan el Error 901 (P126).

    601  Falta el paréntesis de apertura (          while $x < 10 {
    602  Falta el paréntesis de cierre )            while ($x < 10 {

    712  Falta la llave de cierre } del else
    713  El bloque del else está vacío
    714  else sin un if antes
    715  Indentación incorrecta dentro del else
    716  Tabulación en la indentación del else
    717  La llave de cierre } del else no está alineada

    719  La llave { del else está sola en su línea (se permite) pero no está

9. ETAPAS DEL COMPILADOR Y ORGANIZACIÓN DEL CÓDIGO
-------------------------------------------------------------------------------
El código está en  src\proyectocompiladores2 . Cada etapa está marcada en el
código con un comentario "===== ETAPA N =====". Main.java las llama en orden:

  Lectura   io\LectorArchivoPHP.java      Lee el archivo sin cambiarle nada
                                          (guarda el salto de cada línea).
  ETAPA 1   lexico\AnalizadorLexico.java  Obtención de tokens: recorre cada
                                          línea carácter por carácter y la
                                          corta en lexemas.
  ETAPA 2   lexico\ClasificadorTokens.java  Clasificación: dice de qué tipo es
                                          cada token (variable, número, texto,
                                          palabra reservada, comentario...).
  ETAPA 3   lexico\Patrones.java          Patrón: las reglas de cada tipo de
                                          token y las palabras reservadas.
  ETAPA 4   lexico\ValidadorLexema.java   Validación del lexema: usa las reglas
                                          de la carpeta "validacion"
                                          (identificadores, etiquetas,
                                          comentarios).
  ETAPA 5   sintactico\AnalizadorSintactico.java  Análisis sintáctico: revisa
                                          el orden de los tokens según la
                                          gramática (sección 10) y construye
                                          el árbol sintáctico.
              ValidadorEstructuraControl  Parte común de while e if:
                                          "palabra (condición) { ... }"
              ValidadorWhile, ValidadorIf Heredan de la clase anterior.
              ValidadorEcho               Revisa la expresión del echo.
              ValidadorIndentacion        4 espacios por nivel, sin tabulaciones.
              TipoBloque                  Qué número de error usa cada estructura.
              arbol\Nodo...               Los nodos del árbol sintáctico.
  ETAPA 6   semantico\AnalizadorSemantico.java  Análisis semántico: recorre el
                                          árbol con la tabla de símbolos
                                          (semantico\TablaSimbolos.java).
  Archivo   io\EscritorLog.java           Crea el archivo -errores.log.
  Errores   errores\CodigoError.java      La lista de errores con su número.
            errores\GestorErrores.java    Guarda los errores de cada línea.

Traducción orientada por la sintaxis (tema 5): mientras el análisis
sintáctico reconoce cada regla de la gramática, construye su parte del árbol
(un nodo While, If, Echo...). El análisis semántico trabaja sobre ese árbol.
Para verlo: java -jar ProyectoCompiladores2.jar -arbol


10. GRAMÁTICA QUE USA EL ANÁLISIS SINTÁCTICO
-------------------------------------------------------------------------------
El análisis sintáctico es "descendente recursivo": cada regla es un método,
y si una regla contiene a otra, su método llama al de la otra.

    programa   -> '<?php' sentencias '?>'
    sentencias -> { sentencia }
    sentencia  -> while | if | echo | estructura | simple
    while      -> 'while' '(' condicion ')' bloque
    if         -> 'if' '(' condicion ')' bloque [ else ]
    else       -> 'else' bloque | 'else' if | 'elseif' '(' condicion ')' bloque [ else ]
    bloque     -> '{' sentencia { sentencia } '}'
    echo       -> 'echo' expresion { ',' expresion } ';'
    expresion  -> valor { operador valor }
    valor      -> cadena | número | $variable [ '[' ... ']' ]
                  | nombre [ '(' argumentos ')' ] | true | false | null
    estructura -> ('for' | 'foreach' | 'function' | ...) cabecera bloque
    simple     -> token { token } ';'

Reglas de formato que se revisan aparte: cada línea dentro de un bloque lleva
4 espacios más que la línea que lo abre, sin tabulaciones, y la "}" va
alineada con esa línea. La "{" puede ir al final de la cabecera o sola en la
línea siguiente, y el else junto a la "}" o en su propia línea; si van solos
en su línea, también van alineados con la estructura.

Cuando encuentra un error, el analizador lo registra y sigue desde el
siguiente punto seguro (";", "{" o "}") para encontrar todos los errores sin
inventar errores falsos en cascada ("recuperación en modo pánico").


11. DECISIONES TOMADAS
-------------------------------------------------------------------------------
Del Proyecto 1:
  - Se revisan todos los archivos que terminan exactamente en ".php" junto
    al programa; no depende de un nombre ni de una ruta fija.
  - Los errores van debajo de la línea donde ocurren (Opción 1), en todo el
    archivo.
  - Numeración: 4 dígitos y un espacio ("0001 <?php").
  - Las variables distinguen mayúsculas ($total y $Total son distintas). Las
    palabras reservadas no (en PHP "IF" e "if" son la misma), por eso $IF
    también es error.
  - Solo "=" y las asignaciones compuestas (+=, .=, ...) son asignaciones;
    "==", ">=", "<=", "!=" son comparaciones.

Del Proyecto 2 (consultadas con la profesora en noviembre de 2026; su
respuesta confirmó o corrigió cada punto):
  - Llaves: la "{" puede ir al final de la línea del while / if / else o
    sola en la línea siguiente, y el else puede ir junto a la "}"
    ("} else {") o en su propia línea. La profesora aclaró que eso no es
    error. Lo que se revisa es que las llaves existan, que correspondan a
    su bloque y que respeten la indentación: si la "{" o el else van solos
    en su línea, deben estar alineados con la estructura (610, 710, 718,
    719). Pruebas: P45, P60, P67, P91, P99 (válidos) y P89 a P93.
  - Un bloque que solo tiene comentarios o líneas en blanco está vacío
    (confirmado por la profesora).
  - Indentación: 4 espacios por nivel dentro de los bloques del while, del
    if y del else, incluidos los anidados (4, 8, 12...), sin tabulaciones, y
    la "}" alineada con la estructura que abre el bloque. Se revisa la
    primera línea de cada instrucción. El código fuera de esos bloques no se
    revisa (confirmado por la profesora). Los comentarios no se revisan.
  - Echo: la sentencia no lleva paréntesis en su código. La profesora
    aclaró que no hay excepciones: es error agrupar (echo ("Hola");) y
    también llamar una función (echo count($notas);) o convertir un valor
    (echo (int) $x;). Se reporta un solo 802 por echo. Los paréntesis dentro
    de una cadena son texto: echo "Hola (Pablo)"; no es error. Si una cadena
    sin cerrar está dentro de un echo se reporta el error del echo (803/804)
    en lugar del general 502, para no repetir el mensaje.
  - For: el enunciado pide while, if y echo, y la profesora confirmó que el
    for no se exige. Se reconoce como bloque, igual que foreach y function:
    sus llaves deben cerrar (505) y lo que tiene dentro define el nivel de
    indentación de un while o un if anidado, pero no se valida su forma ni
    su indentación (prueba P97). elseif y "else if" se validan con las
    reglas del if.
  - Análisis semántico: el enunciado no da una lista cerrada de reglas y la
    profesora confirmó este alcance: una variable no se puede usar antes de
    recibir un valor (901) y no se puede dividir entre el número 0 escrito
    en el código (902). Cada variable se reporta una sola vez, y no se
    reporta si su asignación ya tiene un error léxico parecido (por ejemplo
    $1nombre = "Ana"), porque ese error ya explica el problema.
    No se revisa si la condición de un while o un if compara o asigna: el
    enunciado indica que la condición se considera correcta y solo se
    valida que exista (la profesora lo confirmó, y esa regla se quitó).
    Tampoco se avisa de posibles ciclos infinitos: el enunciado muestra
    "while ($x < 10) { echo $x; }" como ejemplo permitido.
  - Tipos de error: cada mensaje del .log indica si es [Léxico],
    [Sintáctico] o [Semántico], como pidió la profesora. Los ejemplos del
    enunciado usan $x sin darle un valor antes: copiados tal cual a un
    archivo, el while está bien escrito (ningún error sintáctico) pero da
    el "Error 901. [Semántico]" en $x, porque en PHP real $x no existe
    (prueba P98). Por eso la prueba P54 agrega "$x = 0;" primero.
  - Versión de Java: se compila para Java 8, para que funcione en cualquier
    computadora. Se probó con Java 8 y con Java 21.


12. LIMITACIONES
-------------------------------------------------------------------------------
  - Solo se reconocen comentarios de una línea (// y #), como pide el
    enunciado; los comentarios /* */ no.
  - Un texto entre comillas debe empezar y terminar en la misma línea.
  - El contenido de las condiciones de while e if se asume correcto (así lo
    indica el enunciado); solo se revisa que exista.
  - Un "else" y un "if" en líneas distintas ("} else" y en la siguiente
    "if (...) {") se toma como un else sin llaves (Error 711).
  - El análisis semántico no reconoce variables que reciben valor con
    list(...) = ... o dentro de funciones por referencia.
  - Una resta escrita sin espacios entre una variable y una palabra
    ($a-total) se toma como un nombre de variable con guion (Error 203).
  - Los caracteres & | ^ ~ @ y ` no forman parte del alfabeto definido en
    el Proyecto 1 (Error 501), así que los operadores de bits no se
    aceptan. Dentro de un echo tampoco se aceptan una asignación
    (echo $x = 5;) ni un arreglo escrito con corchetes (echo [1, 2][0];).
  - El for, foreach y function no se validan (sección 11): un for mal
    escrito solo se reporta si deja una llave sin pareja (503 o 505) o si
    la palabra for está mal escrita (504).
  - Con miles de niveles de anidamiento (más de los que admite la pila de
    Java) el análisis se detiene: la consola lo avisa y el .log se escribe
    con los errores encontrados hasta ese punto. Con 60 niveles funciona
    normalmente.
  - Cuando faltan llaves en varias estructuras a la vez, la recuperación
    decide por la indentación a qué estructura pertenece cada "}"; si el
    código además está mal indentado, puede asignarla a otra.
